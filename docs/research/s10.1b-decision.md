# S10.1b — Decision: built-in adapters vs. agent self-integration

Status: **Research decision. Recommendation only — no code in this slice.**
Date: 2026-10 (v0.1.0 Beta, commit `1c822e5`).
Inputs: `agent-capability-matrix.md`, `margin-agent-integration-skill.md`,
`agent-manifest-schema.md`, `integration-security-boundary.md`.

---

## 1. The question

> Should Margin move toward **A — more built-in adapters**, or **B — an agent self-integration
> protocol**?

## 2. The finding that reframes the question

**Margin already chose B, and shipped it.** `src/agents/descriptor/spec.js` is a versioned,
validated, closed, data-only integration protocol with a reader catalogue, a composing loader, an
installer, a CLI, an HTTP surface, a real third-party example (`plugins/doubao/`), and a test that
runs the full install → read → uninstall loop. It is in commit `1c822e5`'s history
(`1e6d905`, `d5dd4ba`, and earlier).

So the question is not "A or B". It is:

> **How far should B extend, and where must A remain?**

And the evidence answers that precisely, because the three built-in Agents each have a hand-written
reader for a *stated structural reason* — not because nobody tried to make them declarative.

---

## 3. Evidence from the current architecture

### 3.1 Evidence that B works (for session discovery)

| Evidence | Source |
|---|---|
| "Add an Agent" used to mean editing nine files; the descriptor spec made it data | `compose.js` header |
| A hardcoded allowlist made `margin agent add deepseek` fail outright and a hand-edited registry entry get dropped without a word | `sourceRegistry.js` |
| 豆包 — a non-trivial Agent with a nested layout, mtime-derived timestamps, recovered workspace, and a transcript status extractor — is integrated with **a JSON file and zero Margin code** | `plugins/doubao/agent.json`, `test/agentDescriptor.test.js` |
| The descriptor spec has absorbed five real gaps, each driven by a specific Agent: `executionStatus`, `sessionCapabilities`, `probe`, `homeCandidates`, `scanAbsolutePaths` | `spec.js`, commit history |
| The full loop — install, dry-run, candidate reporting, tombstone removal, enable, uninstall — already exists and is idempotent | `agentInstall.js`, `agentSourceCli.js` |

**Conclusion:** for the session axis, B is not a proposal. It is the current implementation, and it is
cheaper than A by a wide margin.

### 3.2 Evidence that B cannot reach the other axes

Each built-in resource reader fails to be declarable for a *different* structural reason. This is the
core evidence for the decision.

| Agent | Why the reader is hand-written | Expressible as data? |
|---|---|---|
| **Codex** | rate limits come from a JSONL record, but the reader owns archive-inclusive selection (`sessions` + `archived_sessions`), byte-offset incremental reads, an in-process revision-keyed cache, last-known-good across an archive/switch, and a window-reset rule that maps an expired window to `remaining: null` | no — stateful protocol, not a path+extractor |
| **Claude** | the quota is only legitimate after **four independent external proofs**: a switch app's current-provider pointer, its SQLite provider row, its proxy config, Claude's own loopback `ANTHROPIC_BASE_URL`, plus an endpoint allow-list — then a credentialed network call | no — credential + network + interpretation |
| **Pi** | one source, **two** readers (calendar-day JSONL aggregation + credentialed endpoint), classified by parsing a *provider config file*, and explicitly never added together | no — interpretation, and one provider name is a literal in source |
| **Handoff (all)** | the shared Handoff Core consumes Codex-shaped records; Claude and Pi each bring their own extraction layer | no — by design; the spec has no form for it and refused to invent one |

The irreducible three: **a credential**, **a network call**, **an interpretation**. Those are the
capabilities that stay A, and `integration-security-boundary.md` §3 explains why they must not be
delegated to an Agent-generated artifact.

### 3.3 Evidence *against* investing in either option as a program

| Evidence | Source | Implication |
|---|---|---|
| `attentionStatus` is in the capability vocabulary, in `BASE_CAPABILITIES`, in all three built-in descriptors (`false`), and in every session DTO (`'none'`) — and no reader has ever produced it | `sourceRegistry.js`, `compose.js`, `descriptor/builtin.js` | Capability surface is enumerated ahead of implementation and becomes permanent. More self-integration means *faster* surface growth. |
| The flag and the record can already disagree: Pi declares `apiUsage: false` while `piApiUsage.js` produces a `tokenUsage` record | `descriptor/builtin.js` vs `adapters.js#piAgent` | A protocol where the Agent declares its own capabilities will produce declarations that drift from readers unless observation, not declaration, is authoritative. |
| Unknown top-level keys are silently ignored (**G2**) | `spec.js#validateDescriptor` | The single most likely failure of an agent-generated manifest is currently invisible. |
| `quota`/`apiUsage`/`subscriptionQuota` are not cross-checked against `resources.kind` (**G1**) | `spec.js` cross-field block | A manifest can claim a capability with no wiring and validate cleanly — the exact failure the spec says it exists to prevent. |
| `sessions.roots` has no containment check (**G3**) | `readers.js#discoverTranscriptSessions` | A self-declared root can reach outside the declared home. |

### 3.4 Evidence about demand

The repository contains **three** built-ins and **one** plugin. There is no fourth Agent waiting, no
open integration request, and no stated product requirement. Any argument that self-integration is
needed *now* would be an argument about a hypothetical Agent, which the constraints of this research
explicitly forbid.

---

## 4. Decision

> **Continue B, bounded to the session axis. Keep A for resource, runtime, and handoff. Do not start
> a self-integration *program*; ship the enabling checks and one verification command, and gate the
> rest on a real Agent that actually needs it.**

Concretely:

| Axis | Owner | Why |
|---|---|---|
| Session discovery + transcript execution status | **B — declarative manifest** | 豆包 proves it; the catalogue is bounded and auditable |
| Resource (quota / apiUsage / subscriptionQuota) | **A — built-in reader** | credential + network + interpretation; no declarative form without becoming a language |
| Handoff | **A — built-in implementation**, referenced by name only | the spec already refuses to invent a form for it |
| Runtime control (launch / stop / drive) | **neither — does not exist** | no contract today; `runtime.control` pinned `false` in v0.1 |
| Adding a new `kind` to the catalogue | **A — human decision** | the boundary the whole design defends |

This is not a compromise. It is what the evidence says: Margin's cheap, auditable, high-leverage
extensibility is exactly where the Agent has an information advantage (its own layout) and Margin has
no structural barrier (plain files). Everywhere Margin has a structural barrier, the barrier is the
feature.

---

## 5. Should this enter V0.2?

**Conditionally yes — and only as the five items below.** The condition is §7.

Rationale: the research's main output is not a feature, it is **four correctness checks and one
read-only command**, three of which close gaps that already exist independently of self-integration:

| # | Item | Size | Needed even without self-integration? |
|---|---|---|---|
| V1 | **Closed top-level key set** — unknown key is a validation error; `$comment` still ignored (**G2**) | small | **yes.** A typo'd `"resource"` silently disables resources for a human-authored plugin today. |
| V2 | **Resource-family cross-field rules** — `quota` / `apiUsage` / `subscriptionQuota` require `resources.kind !== "none"` (**G1**) | small | **yes.** This is the spec's own stated principle, currently applied to two of four capability families. |
| V3 | **Root containment** — resolved home must not be a root; `sessions.roots` must be contained in the home (**G3**, R1) | small | **yes.** It is a read-scope boundary on a data-driven reader. |
| V4 | **`margin agent verify <manifest>`** — dry-run validation + composition + probe + a bounded read-only sample projection, exiting `verified` / `no_sessions` / `unavailable` / `rejected` | small–medium | no — this is the only item that exists *for* self-integration |
| V5 | **The skill itself** (`SKILL.md` + two JSON Schemas) and the `generatedBy` provenance field | documentation + one optional schema field | no |

**Explicit non-goals for V0.2:** generated adapters, a network/credential resource provider, a runtime
launch descriptor, a plugin registry or marketplace, changing any of the three built-in readers, and
adding any new capability flag.

**Effort shape:** V1–V3 and V5 are configuration-discipline and documentation. V4 is the only new
behaviour, and it is read-only. Nothing here touches the Core, the Application Contract, or the
Runtime Context's read-only discipline (ADR 003).

## 6. Cost and risk of each pure option

Stated so the decision is auditable against the alternatives it rejected.

### Option A only — more built-in adapters

| | |
|---|---|
| **Cost** | Every new Agent is a new reader module, a new descriptor, a new test, and permanent maintenance against an upstream format that Margin does not control. The repository's own count of touch points was nine files per Agent before the descriptor work. |
| **Risk** | Unbounded and *recurring*: each upstream format change is Margin's bug. It also re-erects the allowlist problem — a type with no reader is unusable, and a user cannot even register it usefully. |
| **What it gets right** | It is the correct answer for resource, runtime, and handoff. That is why the decision keeps A there. |
| **Verdict** | Rejected as the *only* direction. The evidence is that A was already reduced to a data problem and it worked. |

### Option B as a program — full self-integration protocol

| | |
|---|---|
| **Cost** | New format or spec growth, a validation/verification layer, a redaction scanner, and documentation — plus the perpetual cost of every new declarative knob, which is permanent public surface. |
| **Risk** | The manifest surface grows faster than the reader catalogue (evidence: §3.3). Capability-before-implementation is a demonstrated failure mode in this repo. A self-declared manifest is a claim by an interested party, and self-integration turns a small number of reviewed manifests into an unbounded number of unreviewed ones. |
| **What it gets right** | It matches the actual information advantage, and 豆包 shows the payoff is real. |
| **Verdict** | Rejected *as a program*. Adopted *as the existing bounded mechanism plus verification*. |

### The chosen middle — bounded B + verification, A elsewhere

| | |
|---|---|
| **Cost** | V1–V5 above: three small validation rules, one read-only verb, one document, one optional field. |
| **Risk** | Mostly the R1–R8 catalogue in `integration-security-boundary.md`; R1 and R3 are the ones worth real attention. Residual risk is bounded because the manifest can never execute anything and the Runtime Context stays read-only. |
| **Payoff** | Closes three pre-existing correctness gaps (V1–V3) regardless of whether anyone ever runs the skill; gives a real fourth Agent a cheap path; and produces a *measurable* answer to §7 instead of an argument. |

## 7. The gate

V4 and V5 are worth building only if the answer to one question is yes:

> **Is there a specific, real Agent that someone wants to use with Margin, whose session store is
> plain files and whose integration is currently blocked?**

If **yes** → build V1–V5, then run the spike in §8.
If **no** → build V1–V3 anyway (they are bug fixes against the spec's own stated principle) and stop.
Publish the skill as documentation only, with no `verify` verb, until an Agent needs it. This is the
cheapest correct action and it does not require predicting anything.

The gate is a real question because "a fourth Agent" is not a hypothetical the architecture should
optimise for. The constraint in force — do not assume future requirements — applies here most of all.

---

## 8. Recommended next step

**One bounded spike: S10.2 — "unaided self-integration of one real Agent".**

Procedure:

1. Pick **one real Agent** that is not currently integrated and that someone actually uses. Not a
   hypothetical, not a synthetic fixture.
2. Have that Agent execute `SKILL.md` **unaided** — no Margin engineer reading the Agent's source, no
   hand-holding, no code changes during the run. Hand it only the skill and the schemas.
3. Install the emitted manifest with `--dry-run` first, then for real.
4. Record, without adjusting anything:
   * how many attempts before the manifest validated;
   * which fields it got wrong and which check caught them;
   * every capability it correctly reported as `false` / `refused`, and every one it over-claimed;
   * whether Stage 3 projected ≥ 1 correct session DTO;
   * every point where the Agent needed Margin to change code to proceed.

Exit criteria — the spike succeeds only if **all** hold:

| # | Criterion |
|---|---|
| 1 | The manifest passes validation, composition, and probe with **no Margin code change**. |
| 2 | Stage 3 projects at least one session with a real native id, a resolvable workspace, and parseable timestamps. |
| 3 | Every capability the Agent cannot deliver is `false` and appears in `report.requests[]` — none is over-claimed. |
| 4 | The redaction scan finds no credential-shaped value in either artifact. |
| 5 | The uninstall round trip is clean, and detection does not resurrect the Agent. |

Failure interpretation, decided in advance so it cannot be rationalised afterwards:

* **Fails at 1 or 2** → the catalogue is missing a genuinely needed primitive. That is evidence for A
  (a built-in reader or one new declarative form), not evidence to make the DSL more powerful.
* **Fails at 3** → the Agent cannot self-assess capabilities, and the declaration must be *observed*,
  not accepted. Strengthen V4; do not trust the manifest more.
* **Fails at 4** → R3 is real and the redaction scanner is the load-bearing control, not the skill's
  rules.
* **Fails at 5** → the registry/tombstone logic needs work before any of this matters.

Measured, this spike produces the only evidence that can decide whether S10.3 exists.

## 9. Reversibility

| Change | Reversible? |
|---|---|
| V1–V3 (validation rules) | Yes, one block each — but they should not be reversed: they refuse a silent failure. A previously-valid descriptor that relied on the ignored key or the unwired capability is now loudly rejected, which is the intended direction. Call it out in the changelog. |
| V4 (`agent verify`) | Yes, trivially — a read-only verb with no persistent side effect. |
| V5 (skill + `generatedBy`) | Yes — documentation, plus one optional schema field no behaviour branches on. |
| Any future new `kind` | No, never. That is the irreversible step, and it is gated on a human decision precisely because of it. |
| The three built-in readers | Untouched by this research. |

---

## 10. Decision summary

| Question | Answer |
|---|---|
| **A or B?** | **B already exists for sessions; keep it there.** Keep **A** for resource, runtime, and handoff, because each has a stated structural barrier (credential, network, interpretation, distiller) that a manifest must not be allowed to cross. |
| **Enter V0.2?** | **Conditionally.** Ship V1–V3 unconditionally (they are pre-existing correctness gaps), and ship V4–V5 only if §7's gate is answered yes. |
| **Biggest risk** | R1 (path over-reach from an uncontained declared root) and R3 (credential disclosure by the skill), both with concrete, small mitigations. |
| **Biggest architectural risk** | Declarative-surface growth outrunning the reader catalogue — the `attentionStatus` precedent. Every new `kind` is permanent. |
| **Next step** | S10.2: one real Agent, unaided, five exit criteria, interpretation decided in advance. |
