## S1 — Session Truth

- **Problem:** The default resumable surface can contain duplicate logical sessions and sessions that have been archived or removed at the native source.
- **Status:** `CLOSED`
- **Scope:** Codex source discovery, canonicalization, resumable eligibility, CLI selection, HTTP DTOs, and Electron/React refresh. Canonical key direction: `agent + sourceId + nativeSessionId`; physical rollout path is provenance/location, not identity.
- **No-go:** Do not hide records only in React; do not mutate Codex files, indexes, or state DB; do not conflate `session_id` and a rollout filename; do not retain deleted items as a historical cache in the default resumable list.
- **Acceptance:**
  - A normal list contains each active logical session once, even if it has multiple physical rollouts.
  - A move from `sessions/` to `archived_sessions/` removes the item on the next discovery/refresh.
  - A native-file deletion removes the item on the next successful discovery/refresh.
  - Archive/deletion semantics, identity, ordering, and filtering are identical for CLI and Electron.
  - Lifecycle and resumable eligibility are decided before page limits and workspace grouping.
- **Evidence:**
  - Margin currently recursively scans both `sessions/` and `archived_sessions/` in `src/core/handoff/session-source.js`, creates `id` from the rollout filename, deduplicates only that filename-derived value, and then filters only `thread_source`.
  - The local source contained 7 active and 91 archived rollout files. Five native `session_id` values mapped to more than one physical rollout (user root plus subagent/control rollouts); one root-session id appeared in both active and archived trees. Filename id and payload `session_id` differed for six rollout files.
  - Upstream Codex’s normal `get_threads()` lists only the `sessions` root; upstream exposes a separate archived-path lookup and its persistence contracts use a logical thread/session id plus optional rollout path. [Upstream list source](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/list.rs) and [thread-store types](https://github.com/openai/codex/blob/main/codex-rs/thread-store/src/types.rs).
  - Electron loads `/api/sessions`; that endpoint and the CLI both call the shared source discovery, but the Electron renderer retains its last list if a quiet poll fails and polls only on focus/every 30 seconds while expanded.
- **Decisions:**
  - Default resumable means active only. `archived_sessions/` is not a candidate root for this list.
  - Native `payload.session_id` is the source-session portion of the canonical key when valid; a filename-derived rollout id is only a guarded legacy fallback/provenance field.
  - A source registry id (not the display name `Codex`) supplies `sourceId`; therefore a future second Codex source cannot collide with the active one.
  - If an active and archived physical copy is observed during a race, active wins for the active-list projection. Archive must never win merely because its file mtime is newer.
  - Discovery is snapshot based: a successful refresh replaces the entire renderer list; an error may retain a clearly stale list only until the next success, with stale/error state explicit.
- **Result (2026-09-07):** Completed. Active-only discovery now derives `nativeSessionId` from `payload.session_id` with filename fallback retained as `rolloutId` provenance; it filters lifecycle/internal eligibility, canonicalizes by `agentType + sourceId + nativeSessionId`, then sorts and applies limits. CLI and Electron HTTP both invoke the Codex adapter with the registered source id. A successful Electron list response already replaces the complete renderer snapshot, so deleted files disappear at the next successful refresh.
- **Validation:** `test/marginSessionTruth.test.js` covers payload/filename divergence, duplicate rollouts, archived-only and active/archive collision behavior, deletion after a successful refresh, filter-before-limit, source-id separation, and CLI/HTTP parity. Focused session/CLI/HTTP tests passed (32/32); production web build passed.
- **Next action:** S2 — define the source snapshot revision contract and evaluate filesystem watching plus periodic reconciliation for realtime propagation.

## S2 — Realtime Session Sync

- **Problem:** New, changed, archived, and deleted sessions are observed through polling, so propagation is delayed and source changes lack an explicit revision contract.
- **Status:** `CLOSED`
- **Scope:** Source snapshots/revisions, filesystem-watch versus bounded polling evaluation, HTTP refresh contract, Electron state updates.
- **No-go:** Do not introduce a renderer-owned shadow session store or a lossy event stream without snapshot reconciliation.
- **Acceptance (R1 latency/behavior targets, to be proven by the R1 benchmark):**
  - With the window visible and the Board expanded, a native create/update/archive/delete is reflected as a replaced snapshot with P50 ≤ 0.5 s and P95 ≤ 1 s measured from the filesystem operation to the DOM row change on this machine.
  - A transient poll/refresh failure retains the last-known-good list explicitly stale and recovers automatically (no Retry click); a revision read that fails never clears or mutates the shown snapshot.
  - An archived or deleted session cannot reappear from any trigger: triggers never carry session data and every refresh re-reads the source, so a row can return only if a physical rollout for its canonical id exists again.
  - No revision polling runs while the window is hidden or collapsed or the Board is not mounted; expand, focus, and return-to-visible each refresh immediately.
- **Evidence (measured 2026-09-07 on this machine, runtime `node` v22.23.1 win-x64):**
  - Electron renders refresh on mount, expand, window focus, and every 30 s only while expanded; HTTP rediscovery is otherwise request-scoped (`web/src/margin/MarginApp.js`).
  - Full active discovery of the real local source (8 native rollout files, ≈15.6 MB) costs ≈470–495 ms. ≈390 ms of that is per-session `git rev-parse` spawns in `resolveWorkspaceIdentity()` (≈56 ms each), not the discovery itself: full content reads of all 8 files ≈37 ms, recursive walk + `realpath` ≈4 ms.
  - A stat-only signature of the active tree (relative `rollout-*.jsonl` path + size + mtimeMs, hashed) costs ≈0.7 ms per pass — three orders of magnitude cheaper than full discovery. This single fact is what makes bounded revision polling viable where full-discovery polling is not.
  - Node 22.23.1 recursive `fs.watch` on Windows delivered events within ≈1 ms for file create, append-change, in-tree rename, delete, and cross-tree move-out, and — critically — followed newly created nested day directories (`sessions/2026/09/08/…` written through a watcher armed on `sessions/`). Event types are not usable as an operation log: create/delete/rename/move all surface as `rename`, appends surface as `change`, parent dirs also report `change`, and a read-directory buffer overflow aborts the watch with an error.
- **Decisions (R1):**
  - The source snapshot revision contract is a **content-independent filesystem signature**: `sha256` over the active source's registry content (active codex id + path + enabled), the resolved codex home, and the sorted stat list of `rollout-*.jsonl` under `{codexHome}/sessions` as `relativePath|size|mtimeMs`. The signature changes exactly when a native create/update/archive/delete or an active-source change could alter the S1 projection, and costs ≈1 ms.
  - Realtime propagation is **signature-revision polling with snapshot refresh** (the "bounded polling" option), not watcher-first. The renderer polls `GET /api/sessions/revision` every 500 ms only while the window is visible and the Board is expanded, and triggers the existing quiet full refresh only when the returned revision differs from the revision carried by the last successful `GET /api/sessions`. Full discovery stays the single source of truth and stays request-scoped.
  - `fs.watch` / chokidar are **evaluated and deferred** from the R1 minimum. On this small single-profile tree they are reliable in practice, but they duplicate a ≈1 ms signature poll, add an overflow/abort failure mode, and their event types are too ambiguous to act on; a watcher could only ever be a dirty hint. They remain the documented R2 accelerator if 500 ms typical latency is ever insufficient, and the revision endpoint + refresh path are exactly the seam they would plug into.
  - Debounce lives in the renderer refresh scheduler, not in the source read: revision reads are always cheap; full refreshes are coalesced to one in flight, a minimum ≈1 s apart during a live Codex write burst, with one trailing settle refresh after the burst (hard cap ≈2 s). A single isolated change therefore refreshes on the next 500 ms tick; a burst converges within ≈2 s of its last write. Mid-append reads are already safe: S1 parsing freezes at complete lines and skips partial records, and the next write bumps the signature again.
  - Polling is paused when the window is hidden, minimized, or collapsed (Chromium background throttling already self-pauses timers; hide/minimize also flips document visibility). Expand, window focus, and `visibilitychange → visible` each run an immediate refresh (already implemented for focus/expand) and restart the poll. Sleep/resume needs no event: the interval re-fires ≤500 ms after wake and any signature delta made after wake is picked up then.
  - The existing 30 s expanded refresh stays as an independent reconciliation safety net at negligible cost, and is the bound for any residual missed-detection bug.
  - A small per-canonical-cwd workspace-identity cache (TTL ≈10 s, injectable for tests) is part of the minimum so a full refresh costs ≈100 ms instead of ≈480 ms; otherwise refresh CPU during an active Codex conversation is not sustainable at the cooldown above.
- **R1 result (2026-09-07):** Research complete. Windows watcher behavior is measured and recorded, the revision contract is defined, and the minimum architecture is decided (signature-revision poll + replace-on-success snapshot refresh; no watcher in the minimum). S1 lifecycle-correct snapshots are the prerequisite and are closed.
- **Result (2026-09-07):** Implemented. `computeSourceRevision` in `session-source.js` hashes the active source config plus a stat-only list of `rollout-*.jsonl` under `{codexHome}/sessions` (archived_sessions excluded) in ≈1 ms. `httpAdapter.js` exposes `GET /api/sessions/revision` and a `revision` field on every successful `GET /api/sessions`. The renderer (`MarginApp.js`) polls that cheap revision every 500 ms only while the window is visible and the Board is expanded, running one quiet full refresh (coalesced: one-in-flight plus a trailing refresh) only when the revision differs, and an immediate refresh on expand/focus/return-to-visible. A per-canonical-cwd git-root identity cache (TTL 10 s) cuts full discovery on the real source from ≈470–495 ms to ≈85–95 ms steady-state (~167 ms cold) without changing the projection.
- **Validation:** `test/marginSessionRevision.test.js` (signature stable when unchanged; changes on create/append/archive/delete/source-switch; archived_sessions and non-rollout noise never change it; `/api/sessions/revision` and `/api/sessions` stay consistent live) and `marginR3Board.test.js` S2 additions (no polling while collapsed or hidden; unchanged revision triggers no extra full discovery; a change triggers exactly one quiet refresh; return-to-visible refreshes immediately). S1 session-truth, HTTP-adapter, discovery-parity, workspace, CLI, and handoff suites all still pass. Production web build passed.

## S3 — Realtime Resource Telemetry

- **Problem:** Token and quota information needs near-real-time, provider-backed updates without confusing stale values for live truth.
- **Status:** `CLOSED`
- **Scope:** API-token use, subscription 5h/7d quota, refresh cadence, unavailable/stale presentation. Reuses the S2 source-revision live-sync seam; no new SSE/WebSocket/filesystem watcher.
- **No-go:** Do not estimate provider quota from local conversation text; do not overwrite a good reading with an unmarked empty result; never sum or conflate token usage with quota (they are separate resource types with separate semantics).
- **Acceptance (R1 latency target, to be proven by the R1 benchmark):** A native `token_usage_record`/`event_msg.token_count` append to the live active rollout is reflected as an updated resource DTO → DOM row with P50 ≤ 0.5 s and P95 ≤ 1 s measured from the filesystem append to the change on this machine, only while the window is visible and the Board is expanded. Token fields (`input`/`cached input`/`output`/`reasoning`/`total`) and the two quota windows (`5h`, `7d`) are provider-reported, never derived, and never added to each other. Each DTO carries a revision and a freshness timestamp; a failed refresh retains the last-known-good explicitly stale and recovers automatically.
- **Evidence (measured 2026-09-07 on this machine, real Codex home):**
  - The native schema is confirmed. `token_usage_record` (top-level type; 152 lines across the active tree) carries `payload.{thread_id,turn_id,session_id,root_turn_id,response_id}` and `payload.usage{input_tokens,cached_input_tokens,cache_write_input_tokens,output_tokens,reasoning_output_tokens,total_tokens}`, plus cumulative `payload.turn_token_usage` and `payload.thread_token_usage`. Deduplicate per-request usage by `response_id`. `event_msg/payload.type="token_count"` (also 152, one per turn, adjacent to its `token_usage_record`) carries `payload.info.total_token_usage` (that session's cumulative thread total) and `payload.rate_limits{plan_type, primary{used_percent,window_minutes:300,resets_at}, secondary{used_percent,window_minutes:10080,resets_at}, credits, spend_control_reached}`. `token_count` therefore yields **both** the global subscription quota (`rate_limits`, identical across sessions because it is subscription state) and the emitting session's running token total (`info.total_token_usage`). In the live (max-mtime) active rollout, the latest complete `token_count` is authoritative for both. Model is **not** on either record; `session_meta` carries `model_provider` and the model in `base_instructions` text, so model must be resolved at read time for provenance. A trailing partial record from an in-flight/aborted write is present in live files and must be skipped (complete-line freeze), confirming S2's mid-append read convention carries over.
  - Root cause of lag: `loadResources()` runs only on mount, expand, window focus, and the 30 s expanded interval (`web/src/margin/MarginApp.js`). It is **not** fed by the S2 500 ms revision poll — that effect only calls `loadSessions()`. So quota/usage updates ride the 30 s clock, not the near-real-time source sync. Separately, each `GET /api/resources/status` call currently does a full recursive content read of `sessions/` **and** `archived_sessions/` (`readLatestCodexQuotaSnapshot`), which is why it was never polled at 500 ms.
  - S2's `computeSourceRevision` already signatures exactly the tree S3 cares about: it stats `{codexHome}/sessions/rollout-*.jsonl` and changes precisely on an append/create/archive/delete. Because `token_usage_record` and `token_count` are appended to those very files, a resource event **already bumps the S2 source revision** — no separate resource revision contract and no watcher is needed. Cost to detect a resource change is therefore ≈0.
  - Full active-tree content scan of the real 8-file source is ≈37 ms (excluding the git spawns that dominate discovery but are absent from the resource path); an incremental tail of only the appended bytes of one live rollout is sub-millisecond and O(appended) per refresh, never O(file) per poll tick.
- **Decisions (R1):**
  - Reuse the **S2 500 ms signature-revision poll as the sole dirty detector** for resources (resource events are appended inside the very tree the revision watches) and refresh resources on the same revision-diff → cooldown/trailing-settle path as sessions. No new revision endpoint, no watcher, no SSE/WebSocket.
  - The content refresh is an **incremental JSONL tail of only the live active rollout**, tracked by an in-process per-rollout `{path, size, offset}` map. On a detected revision change, for the live rollout (the active rollout with the greatest mtime) whose size grew, read bytes `[offset, size)`, split into complete lines, scan only those new lines for the newest `token_count`, and advance `offset` to the end of the last complete line. A session switch (a different rollout becomes max-mtime, or a new rollout appears) resets that file's offset and tail-reads it so the bar follows whatever conversation is currently running. This is the **combined** option — resource-revision polling for liveness + incremental tail for content — and is the recommended minimum. It avoids both a full scan per 500 ms tick and any offset bookkeeping for the never-changing archived tree.
  - Live resource reads are bounded to the **active** `{codexHome}/sessions` tree only, matching S1/S2 lifecycle semantics. `archived_sessions` is frozen history and out of the near-real-time projection; Codex rewrites current subscription quota into whichever active session is live, so active-only reads stay authoritative for live quota.
  - A tiny **in-process resource-state cache keyed by source revision** sits in the resource service/HTTP boundary so an unchanged revision returns the cached DTO without rescanning (the 500 ms poll and the 30 s reconcile are then both cheap). Quota stays a latest-snapshot (state) read; token usage stays a live cumulative read for the live session. If tail-offset bookkeeping ever proves fragile on a real burst, the accepted fallback is a revision-keyed full **active-tree** content scan (≈37 ms, no git) run only on a revision change under the same ~1 s cooldown — never per 500 ms tick.
  - Token and quota are separate `resourceType`s in the DTO and are never added. `event_msg.token_count.rate_limits` → two `quota` windows (`5h` = 300 min, `7d` = 10080 min) unchanged from today. `event_msg.token_count.info.total_token_usage` → one `tokenUsage` record for the live session carrying `{inputTokens, cachedInputTokens, outputTokens, reasoningTokens, totalTokens, model, sessionId, threadId, responseId, updatedAt}`. Field mapping is verbatim provider naming: `cached_input_tokens`→`cachedInputTokens` (cache-read), `output_tokens`→`outputTokens`, `reasoning_output_tokens`→`reasoningTokens`, `total_tokens`→`totalTokens`. `cache_write_input_tokens` is preserved on the S4 store but not surfaced in the live token display.
  - Every resource DTO carries a `revision` (the source revision it was read under), a per-agent `freshAt`, and per-agent `stale`/`unavailable` flags. A refresh that fails or reads no trusted complete `token_count` returns the cached last-known-good marked stale (never an unmarked empty/zero that could be mistaken for live truth). The renderer advances resource state only on a trusted snapshot.
  - Copy / Save / Generate do **not** need a forced reconcile. Copy copies row metadata; Save writes caller-provided markdown; Generate already re-reads the source fresh via `captureSession`/`readSessionMetaSource` (frozen at the last complete line). If a handoff document should embed current usage, that usage must be read from the capture Generate just froze — read-time truth, not the bar's revision-keyed cache — rather than forcing the live bar to flush.

  1. **Persisted event = one provider request.** Every ingested complete native `token_usage_record` becomes one immutable log line (schema `v1`, `kind:'usage'`): `{ v:1, kind, agent:'codex', sourceId, provider, model, sessionId, threadId, turnId, rootTurnId, responseId, ts, capturedAt, usage:{input,cachedInput,cacheWrite,output,reasoning,total}, turnUsage, threadUsage, provenance:{home, rel, role:'active'|'archived'} }`. `usage` is the verbatim per-request bucket set (camelCased, nullable members allowed); `turnUsage`/`threadUsage` are provider cumulative sidecars stored for audit/reconciliation only and never summed into cost; `provider`/`model` are resolved once per rollout from its `session_meta` (nullable). `total` is the provider `total_tokens` verbatim.

Archive: a runtime archive is just the file leaving the active projection (already ingested); an archive that happened while Margin was closed is ingested from `archived_sessions` at the next catch-up. Source switch: the tailer re-resolves the active source per pass (S2 convention) and re-arms; each event is stamped with its own `sourceId`, so switching never corrupts a series. Partial line: complete-line freeze everywhere (S2/S3 convention); the store additionally self-heals by truncating its own trailing partial line before catch-up. Native deletion: already-ingested records remain as durable fact — telemetry outlives the native file, which is exactly what makes historical A/B queries possible.

Price table rows `{provider, model, from, buckets:{input,cachedInput,cacheWrite,output,reasoning}, currency}` (per-1M-token rates; aliases such as `reasoning→output` are explicit table policy). A record with an unknown model or a missing bucket rate is reported `priced:false` with the unpriced bucket tokens listed — never silently estimated. Relative A/B cost comparisons that keep model and price table identical are price-independent (cost ratio == token ratio) and need no table at all. The bucket-sum-vs-`total_tokens` mismatch (0/152 equal) is surfaced as a labeled reconciliation diagnostic, separate from any cost figure.

Benchmarks are external cohort manifests (the existing `run-ledger.json` shape: entries carrying `caseId`/`arm`/`sessionId`/`startTs`/`endTs`/`model`) consumed by the report tool; Margin never needs benchmark knowledge embedded in the log. ### S4.1 — Development token-cost audit (analysis only, 2026-09-07/08)

Read-only audit of the live telemetry store (`~/.margin/telemetry/usage.jsonl`, 1,383 provider requests across 92 Margin-repo sessions, Sep 5–7) plus the matching native rollouts. No product code changed. Findings are correlational to native tool activity, not causal.

**Most token-heavy session / requests.** Biggest by raw input: `01a07564` (145 req, input ≈14.0 M, cached ≈13.8 M), then `01a070e6` (57 req ≈6.5 M), `01a0797a` (61 req ≈5.2 M). Within every session the 5 largest requests are always the final 5 requests — a monotonic-context signature, not a tool spike. The deepest native dive (`01a07bda`, the actual S1 Session-Truth implementation session) shows the largest inputs are also the last turns.

**Input vs session length.** Per-request `input_tokens` grows monotonically with request index: late-quarter median / first-quarter median = 1.5×–3.7× (e.g. 1.60× at 145 req; 3.69× at 28 req). Median per-request input ranges ≈58k–109k across sessions; long sessions reach ≈118–175k late. Each request re-sends essentially all accumulated history, so input tracks cumulative context length.

**New context per request is small and steady.** Mean new context per request (input delta) ≈0.7k–5.8k across audited sessions; within-run single-step growth rarely exceeds ≈10–15k and the one >20k "step" per session is the cold-start first request (≈23–24k). This means a long session's raw input is dominated by re-sending accumulated context, not by per-turn novelty.

**Cache.** `cached_input_tokens`/`input_tokens` ≈91–98.5% (usually >95%). So ~97%+ of input each request is a cache-served prefix re-read; only ≈1.5–4% is fresh. Cache hit ratio is lower in the first few requests of a session (≈60–71%) and rises as the prefix accumulates — i.e. new-session starts are less cache-friendly.

**Tool activity vs token peaks (native correlation, 3 sessions).** Spearman-style correlation between next-request input delta and preceding tool-output tokens was weak/inconsistent: ≈0.08 (S1 session), ≈−0.02, ≈0.36. Correlation with #files-read was ≈0.67 in the S1 session (one or two multi-file `Get-Content -Raw` turns) but ≈NaN/−0.06 elsewhere. Large tool outputs do occur (multi-file reads and `npm test` ≈20–30k tokens, truncated by `max_output_tokens`) but they do not produce a comparable input spike at the next request because context is cache-served and subject to compaction (a 30k-token output step corresponded to ≈1.9k net new input). Repeated same-file reads were minor: ≤2 reads of only a handful of files per audited session (`adapters.js`, `httpAdapter.js`, `marginWorkspaceSessions.test.js` in the S1 session; `SessionBoard.js` in one other). So repeated read/grep/git/test is not a dominant, reproducible token-peak driver in these sessions — the dominant driver is monotonic context carry.

**Long-session context carry vs new-session cold start.** Historical data is NOT sufficient for a fair head-to-head cost comparison: sessions differ in task/tool load, there are no matched task pairs, `input_tokens` conflates the cache-served prefix, and compaction breaks any linear tool-output→input mapping. What is measurable is the mechanism: continuing a session costs a small, steady per-request increment (~1–6k new tokens) on top of a large ~97%-cached re-sent prefix; starting fresh costs a ~24k cold-start base plus uncached re-reads of whatever repo files the agent needs, and starts with a lower cache-hit ratio.

**Recommendation (current guidance, not a proof).** Continue the same session for same-scope bounded follow-ups (fix/test loops on code already in context): marginal new tokens are small and ~97% cache-served, so it is token- (and, on metered API, cost-) efficient per unit of new work and avoids cold repo re-reads. Start a new session (using the plan-checkpoint doc to re-state only what is needed) when: the scope shifts to a different part of the repo, the accumulated context has grown large enough that most of it is no longer relevant to the next task, or after repo-wide churn invalidated much of the carried context. Neither rule is universal; the deciding factor is how much of the accumulated context the next task still needs.

**Controlled A/B — worth it.** Recommended as a follow-up experiment (not run here). Minimal design: pick one bounded task on this repo; fix model and repo `git` state; run a matched pair repeatedly (e.g. 3× each): Arm CONTINUE resumes a long session that already holds ≈100k of repo context; Arm NEW starts a fresh session whose prompt points to the exact relevant files. Measure via `margin cost report` per session (requests, input/cached/output/reasoning) and wall time + test correctness. Mitigate cache conflation by reporting within-thread `cached_input` separately and by flushing provider cache state or noting it; keep prompt wording otherwise identical; balanced order. Report token-ratio first (price-independent) and currency cost only if a price row is configured. Existing isolated run homes from the earlier R7 benchmark are gone, so this A/B must run with a retained, margin-watched home (S4 retention rule).
