# Margin 招聘投递版设计规格

**日期：** 2026-07-29

**状态：** 待用户审核

**目标岗位：** 国内 AI 产品经理

**主要语言：** 中文；保留同构英文速览和现有英文完整案例

## 1. 背景

Margin Case Study 已经具备双语网页、中文 PDF、英文 PDF、10 章完整叙事、6 张脱敏产品截图、4 张策略图和明确的证据边界，并已部署为公开网站。

现有版本适合深度阅读，但招聘方第一次打开页面时仍需自行从长文中提取四项核心信息：

1. 产品解决什么问题；
2. 候选人独立负责了什么；
3. 哪些产品判断最能体现 AI 产品经理能力；
4. 当前成果已经证明什么、尚未证明什么。

本次迭代不重写完整 Case Study，而是在完整内容之前增加一个招聘方可在约 3 分钟内读完的速览层，同时提供 PDF、GitHub 和求职表达材料。

## 2. 目标

### 2.1 用户目标

国内 AI 产品经理招聘方无需读完 10 章，即可准确理解：

- Margin 的产品定位；
- 用户问题与机会判断；
- 候选人的独立职责；
- 三个关键产品决策；
- 已交付的系统与 MVP；
- `Implemented`、`Scenario-validated` 与 `Hypothesis` 的证据边界。

### 2.2 候选人目标

- 提供一个可以直接放入简历和招聘平台的公开链接；
- 提供可下载的中英文 PDF；
- 提供与网页叙事一致的简历描述和面试讲述材料；
- 保留完整案例的深度，不因压缩而夸大证据；
- 让后续更新只需修改结构化内容源，而不是在多个页面重复改文案。

### 2.3 技术目标

- 保持纯静态、离线可打开的网页结构；
- 不新增运行时网络请求、分析脚本、第三方字体或 CDN；
- 保持中英文切换、键盘访问、移动端布局和低动态偏好；
- PDF 与 GitHub 链接在本地和线上部署中均有明确行为；
- 构建时对速览数据和求职材料执行合同测试。

## 3. 非目标

本次不包含：

- 重新设计完整 Case Study 的视觉系统；
- 删除、改写或缩短现有 10 章完整正文；
- 建立独立的第二个作品集站点；
- 增加“速览模式 / 完整模式”切换器；
- 增加邮箱、LinkedIn 或尚未提供的个人主页；
- 增加访问统计、埋点、招聘方追踪或 Cookie；
- 虚构用户访谈、留存率、满意度、转化率或商业结果；
- 实施真实用户研究。用户研究仍是 Case Study 中明确标注的下一阶段。

## 4. 目标受众与阅读场景

### 4.1 主要受众

国内 AI 产品经理岗位的招聘方、用人经理和面试官。

### 4.2 次要受众

- 希望深入理解产品策略与系统设计的产品负责人；
- 需要英文材料的协作方或海外阅读者；
- 面试前需要快速复习项目表达的候选人本人。

### 4.3 典型阅读路径

1. 招聘方从简历或招聘平台打开公开链接；
2. 在首屏识别产品、角色和阶段；
3. 进入 3 分钟速览；
4. 根据兴趣选择完整案例、中文 PDF、英文 PDF 或 GitHub；
5. 对具体决策感兴趣时继续阅读现有 10 章。

页面只有一条连续阅读路径，不要求招聘方先理解新的模式切换。

## 5. 信息架构

网页顺序固定为：

1. **现有首屏**
   - 核心标题；
   - 一句话产品定义；
   - 独立职责；
   - 项目阶段。
2. **行动入口**
   - 3 分钟速览；
   - 查看完整案例；
   - 下载当前语言 PDF；
   - GitHub 项目。
3. **招聘方 3 分钟速览**
   - 问题；
   - 三个关键决策；
   - 独立交付；
   - 证据与边界。
4. **现有章节导航**
5. **现有 10 章完整案例**
6. **页尾入口**
   - 中文 PDF；
   - 英文 PDF；
   - GitHub 项目。

“查看完整案例”直接定位到现有第一章，不创建第二套路由。

## 6. 3 分钟速览内容模型

速览使用单一结构化内容源。语言无关的资源地址放在根级 `resources`，中文和英文共享相同的 `quickRead` 字段：

```text
resources
  fullCaseAnchor
  pdf.zh
  pdf.en
  github
zh
  quickRead
    label
    title
    summary
    problem
      title
      body
    decisions[3]
      title
      body
      evidenceIds[]
    delivery
      title
      body
      items[]
    evidence
      title
      body
      implemented
      scenarioValidated
      hypothesis
en
  quickRead
    与中文相同字段
```

### 6.1 问题

需要表达的核心判断：

> 当用户最需要支持时，往往恰好没有能力先把自己整理成一个清晰提示词。Margin 试图降低“先解释清楚自己，才能获得帮助”的门槛。

该判断继续标记为创作者观察和待验证假设，不包装成用户研究结论。

### 6.2 三个关键决策

固定展示以下三项：

1. **先接住，再推进**
   - 产品不以立即生成任务为默认反应；
   - 先允许模糊表达，再形成可继续的活线。
2. **选择性记忆，而不是无限记忆**
   - 记忆服务于跨会话连续性；
   - 临时情绪不能自动成为长期身份；
   - 被召回的内容需要有当前相关性。
3. **低压力行动，而不是任务接管**
   - 只抬升一个可拒绝、可完成、可替换的下一步；
   - 不使用积分、连续打卡或惩罚性提醒制造推进。

每项必须绑定现有证据编号，不新增无法追溯的产品主张。

### 6.3 独立交付

明确用户独立承担：

- 产品定位与问题重构；
- MVP 范围和非目标；
- AI 行为、记忆与状态机制；
- 信息架构与视觉表达；
- 前后端实现、测试、验收和部署。

不得使用“领导团队”“跨部门推动”或其他不存在的团队叙事。

### 6.4 证据与边界

速览必须同时呈现：

- **Implemented：** 产品闭环和主要页面已经实现；
- **Scenario-validated：** 自动化测试和预设场景通过，且验收发现过真实缺陷；
- **Hypothesis：** 目标用户是否需要这种连续性、是否把产品理解为陪伴空间，仍需外部研究。

“尚未真实用户验证”不能藏在完整案例末尾，必须在速览中可见。

## 7. 首屏和行动入口

### 7.1 首屏文案层级

保留核心标题：

> Margin：为尚未整理好的自己，留一个位置

标题下方依次呈现：

- 一句话定义：以“第二自我”为关系定位的个人 AI 连续性空间；
- 角色：独立 AI 产品经理 / 产品设计与实现；
- 阶段：可运行 MVP；技术与场景验证完成；真实用户验证待进行。

### 7.2 入口行为

| 入口 | 中文标签 | 英文标签 | 行为 |
|---|---|---|---|
| 速览 | 3 分钟速览 | 3-minute overview | 定位到 `#recruiter-summary` |
| 完整案例 | 查看完整案例 | Read full case study | 定位到现有第一章 |
| PDF | 下载中文 PDF / 下载英文 PDF | Download Chinese PDF / Download English PDF | 打开或下载对应同源 PDF |
| GitHub | GitHub 项目 | GitHub project | 打开 `https://github.com/YJ-Q/Echo` |

语言切换后，PDF 主入口跟随当前语言；页尾同时提供两个 PDF。

GitHub 为外部链接，应清楚标记，不伪装成站内导航。

## 8. 求职表达材料

新增中文文件：

```text
case-study/content/job-application.zh.md
```

该文件不在公开网页正文中自动展示，但随源项目和备份归档保存。

### 8.1 简历项目描述

要求：

- 3–4 行；
- 先写产品问题和个人职责，再写交付与证据；
- 不使用未经验证的业务结果；
- 测试数据必须说明是工程或场景证据，而非用户价值指标。

### 8.2 60 秒项目介绍

结构：

1. 用户处境；
2. 产品重构；
3. 三个关键决策；
4. 独立交付；
5. 当前证据边界。

正常语速下目标长度为 180–260 个中文字符。

### 8.3 5 分钟面试讲述稿

结构：

1. 为什么选择这个问题；
2. 为什么不是任务管理器；
3. MVP 如何形成闭环；
4. AI 和记忆设计中的关键判断；
5. 验收发现了什么；
6. 下一轮真实用户验证如何进行。

### 8.4 八个高频追问

必须覆盖：

1. 为什么这不是普通聊天机器人？
2. 为什么不直接做任务管理器？
3. 没有真实用户数据，如何证明项目价值？
4. 选择性记忆如何避免打扰和误判？
5. AI 在产品中承担什么，确定性系统承担什么？
6. 你独立完成了哪些工作？
7. MVP 为什么选择这些能力、没有选择哪些能力？
8. 如果获得下一轮时间，你最先验证什么？

回答必须与完整 Case Study 一致，不能在面试材料中提高证据等级。

### 8.5 投递链接组合

材料末尾提供三种使用方式：

- 简历：公开网页链接；
- 招聘平台补充材料：公开网页 + 中文 PDF；
- 英文沟通场景：公开网页英文模式 + 英文 PDF。

## 9. 内容与构建架构

### 9.1 单一内容源

新增结构化速览源：

```text
case-study/content/recruiter-summary.json
```

包含根级 `resources` 以及 `zh`、`en` 两个语言对象。构建脚本读取并校验该文件，再把 `resources` 和各语言的 `quickRead` 写入现有 `content.generated.js`。

不在 HTML 和 JavaScript 中手写两份速览文案。

### 9.2 构建数据流

```text
case-study.zh.md ─┐
case-study.en.md ─┼─> build-web.mjs ─> content.generated.js
recruiter-summary.json ─┘

content.generated.js
        +
case-study.js
        ↓
双语速览 + 现有完整案例
```

### 9.3 运行时渲染

`case-study.js` 增加独立的速览渲染函数，职责仅包括：

- 根据当前语言读取 `quickRead`；
- 渲染四个速览部分；
- 渲染当前语言的 PDF 入口；
- 保持现有章节渲染和语言切换逻辑不变。

速览不是第 11 章，不进入现有章节编号与证据章节导航。

### 9.4 静态资源

部署包必须包含：

```text
index.html
web/
assets/
dist/margin-case-study.zh.pdf
dist/margin-case-study.en.pdf
```

网页内 PDF 路径保持相对路径，使本地 `file://` 和线上同源部署都能工作。

## 10. 视觉与响应式

沿用现有编辑式证据视觉：

- 暖纸背景；
- 墨色正文；
- 陶土红重点；
- 清晰分隔线；
- 无渐变；
- 无高饱和科技装饰。

速览区使用现有排版变量和间距系统，不建立第二套设计系统。

### 10.1 桌面端

- 首屏入口保持一眼可见；
- 速览四部分形成清晰阅读节奏；
- 三个关键决策可以横向排列，但不得压缩正文到难以阅读。

### 10.2 移动端

- 390px CSS 视口下不出现水平溢出；
- 入口按钮最小高度 44px；
- 三个决策改为单列；
- 长标题、英文单词和 GitHub 标签不得截断；
- PDF 与 GitHub 入口可键盘访问并具有可读焦点状态。

### 10.3 动态

不新增必要动画。若沿用现有进入效果，必须支持 `prefers-reduced-motion`，且不影响内容立即可读。

## 11. 可访问性

- 速览使用语义化 `section` 和标题层级；
- `#recruiter-summary` 可被跳转后正确识别；
- 内部锚点不依赖 `scrollIntoView`；
- PDF 链接说明语言和文件类型；
- GitHub 外部链接具有明确文本；
- 语言切换后更新速览内容和相关 `aria-label`；
- 不用颜色单独表达证据等级；
- 表格或证据列表在窄屏保持可读。

## 12. 错误处理与降级

### 12.1 构建期

以下情况直接让构建或合同测试失败：

- `recruiter-summary.json` 缺少中文或英文；
- 决策数量不是 3；
- 缺少证据字段；
- PDF 文件不存在或为空；
- GitHub URL 不是预期仓库；
- 中文求职材料缺少规定章节；
- 速览出现禁止的用户指标或伪造引语模式。

### 12.2 运行时

构建产物通过合同后，运行时不发送网络请求。

如果 `quickRead` 意外缺失，完整 Case Study 仍应可读，页面不得因速览渲染错误而整体空白；控制台应给出清晰错误，速览容器显示简短降级提示。

如果浏览器不支持 `download` 属性，PDF 链接仍可在同源页面中打开。

## 13. 测试策略

### 13.1 内容合同

验证：

- `zh`、`en` 速览字段完整；
- 两种语言均恰好包含 3 个关键决策；
- 所有速览证据编号存在于 evidence map；
- 中文求职材料包含 5 个规定部分和 8 个追问；
- 不含虚构团队、用户原话、留存率或满意度结论。

### 13.2 Web 合同

验证：

- HTML 存在速览容器和四类入口；
- 当前语言 PDF 链接正确；
- GitHub URL 正确；
- 速览不进入 10 章导航；
- 中英文切换同时更新速览和正文；
- 现有离线、无外部依赖合同继续通过。

### 13.3 资源合同

验证：

- 中英文 PDF 存在且非空；
- 部署包包含 PDF；
- 所有截图和策略图路径保持有效；
- 隐私扫描覆盖新增 JSON、Markdown 和网页内容。

### 13.4 响应式与浏览器验收

至少检查：

- 1440×1000 桌面视口；
- 390×844 移动视口；
- 中文模式；
- 英文模式；
- 键盘 Tab 顺序；
- 速览与完整案例锚点；
- PDF 与 GitHub 链接。

移动视口要求 `documentElement.scrollWidth === innerWidth`。

### 13.5 回归

- Case Study 专项测试全部通过；
- Echo 项目全量测试全部通过；
- 隐私扫描零发现；
- `git diff --check` 通过。

## 16. 完成标准

只有同时满足以下条件才算完成：

1. 招聘方在完整案例前可以读到双语 3 分钟速览；
2. 首屏和页尾入口均可访问完整案例、正确 PDF 与 GitHub；
3. 中文求职材料包含简历描述、60 秒介绍、5 分钟讲述稿、8 个追问和投递建议；
4. 速览与完整案例的产品主张和证据等级一致；
5. 390px 移动视口无水平溢出；
6. 中英文切换更新速览、入口和完整正文；
7. 本地、测试和线上环境中的 PDF 路径有效；
8. 专项测试、全量测试、隐私扫描和格式检查通过；
9. 线上部署成功并完成关键资源检查；
10. 实施记录更新到 `case-study/REVIEW.md`。
